## User Prompt

/design-discussion of the new question type "Put in order". A spec is already written in @docs/design-put-in-order.md. i found some gaps that need to be verified and addressed  1. Re-saving re-scrambles and corrupts history. Stored orderedIndices in session_scores
    refer to the config.items order at play time. The host game-over summary, the HTML report, the
    CSV export and the player recap all re-read the current config.items. Any later save, even a
    prompt typo fix, reshuffles the items, so every past session's report then shows wrong answers and a
    wrong distribution. The spec "accepts" the reshuffle and even suggests re-saving as the
    anti-cheating mitigation, which makes it worse. A fix is needed (see the decision below).
 2. The HTTPException(422) in authoring_service breaks the layer rule. services/CLAUDE.md:
    "No FastAPI/Socket.IO imports here." common/exceptions.py has BuzzerError subclasses (there is
    no 422 one), and BundleError is mapped to 422 by routers. The spec must name the mechanism: a new
    BuzzerError subclass with status 422 (for example ValidationFailedError in
    common/exceptions.py), or raise ValueError and have both routers map it. It should also say to
    validate the merged values before assigning them to the ORM object, so a failed PATCH can't
    leave a dirty object in the session that get_db commits after the response.
 3. bool is an int in Python. "List of ints" checks (gateway, correct_order, scoring)
    accept [True, 0, 2]. sorted treats it as [0,1,2], so it passes. The spec should say
    type(x) is int, which excludes bool, in all three places, and add a unit-test case for it.
 4. The e2e expects something the spec never builds. E2E step 2 says "player results screen shows
    … the correct order", but the player ResultsPage change only adds "You answered: A → B → C". The
    spec should either add a "Correct order: …" line to ResultsPage (as fill-in-the-blank shows
    accepted answers) or change the e2e assertion.

 Should fix (unstated assumptions an implementer would have to guess)

 5. Other code paths that interpret answer_data per type are missing. The context docs list
    these, but the spec never mentions them:
    - state_service.restore_from_mysql rebuilds the Redis distribution hashes. Does it branch per
      type? If so, it needs "{i}@{p}" keys too.
    - export_service raw per-question CSV: how is an orderedIndices answer rendered (item texts
      joined with "→", or raw JSON)?
    - authoring_service.import_game_bundle: does it validate through QuestionCreate? If not, an
      import bypasses validate_put_in_order. Export needs no change, because it carries
      config/answer_data verbatim.
 6. Payload availability is assumed, not stated. The player ResultsPage and GameOverPage need
    config.items to render texts, and the host ResultsPage needs the raw distribution dict (not an
    index-array transform). The spec should state which payload field supplies each one
    (question_results / game_over summaries), or say "add config to X if absent".
 7. COMPLETENESS chart semantics are undefined. "One bar per item labelled with its average
    position" does not say what the bar length is, or how to show an item no one answered. The report
    COMPLETENESS chart has the same ambiguity. Suggestion: bar label = item text, value = number of
    responses, caption = "avg position 2.3". Or simpler: skip the chart for COMPLETENESS and show the
    average-position list.
 8. The host GameOverPage QuestionCard is ambiguous. Other types show distribution bars there.
    Should put_in_order reuse the ResultsPage bar builder, or show only the correct order and
    counts? The spec says the latter, but say explicitly "no bars" or "same bars as ResultsPage".
 9. The player QuestionPage locked and submitted states are unspecified. Rows and Lock-in must be
    disabled while locked or after submit, and picked should clear when a lock arrives. The other
    branches already do this, but the new branch has its own state.
 10. The editor's COMPLETENESS "may also send correct_order" is optional. Make it always
     send it. Otherwise a later COMPLETENESS→ACCURACY switch in the editor goes through
     questionToForm, which uses the scrambled config.items as the "correct" order, and the author's
     order is silently lost.
 11. Item limits and escaping. Set a max item length (match the MC option limit, or say "none").
     Item text goes into the hand-rolled HTML report, so state that it must be HTML-escaped there.
     Also say whether items are bleach-sanitised like prompts.
 12. Host projector numbering. A scrambled list numbered "1. 2. 3." implies a position. Use
     letters or bullets (cosmetic; decide once).
