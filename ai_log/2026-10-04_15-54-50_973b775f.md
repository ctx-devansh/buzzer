 2. Critic: holes found

 1. A played COMPLETENESS question without correct_order can't be saved, and the editor may
    crash on it. For an imported question with no correct_order, pioStored.correct_order
    is undefined, so the equality check in buildPioPayload throws. Even if that is guarded,

    → Fix in the spec: if the stored correct_order is absent and the items are unchanged,
    resend config.items verbatim and omit correct_order. State this as an explicit exception
    to "always sent". Add a unit or integration test for it.
 2. Changing a played question of another type into put_in_order isn't blocked. The
    guard runs only when the stored type is put_in_order. A played MC question can become
    put_in_order. Its old {selectedIndex} rows then reach the new readers: the
    get_host_question_summary distribution, the report, and the player recap. Those readers
    will crash or misread the rows.
    → Fix: return 409 when the question has session_scores rows and either the old or the
    new type is put_in_order. Also require every orderedIndices reader to skip rows whose
    answer isn't a valid permutation.
 3. Partial credit has no defined display. is_correct is true only for a perfect order.
    A player who scored 833/1000 would see "Incorrect" on the player ResultsPage and ✗ in the
    GameOverPage recap, and would get the "correct answer when you missed" line. The spec
    doesn't decide whether to show something like "Partially correct" or ◐.
    → Recommendation: show "Partially correct" on ResultsPage and ◐ in the recap whenever
    0 < points < points_value. Add it to the player bullets and to the e2e test.
 4. Rounding is wrong when points_value isn't a whole number. points_value is a float.
    With pv = 10.5 and a perfect order, int(quantize(10.5)) gives 11, not 10.5, while
    COMPLETENESS awards exactly 10.5. A perfect ACCURACY score then differs from points_value
    and can exceed maxPossibleScore (host histogram, Canvas CSV).
    → Fix: when c == t, return points_value unchanged. Also state what type
    ScoreResult.points holds (int or float) and keep the rounding consistent with the other
    types, or else require integer points_value for this type.
 5. The bar-chart denominator is not stated. Each answer adds n counts to the distribution.
    If buildBars, _render_bar_chart or the host GameOver bars scale widths by the sum of
    counts, the put_in_order bars come out about 1/n as long. The spec only says that a zero
    count gives a zero-length bar.
    → Fix: state that bar width = count ÷ number of players who answered (or ÷ the maximum
    count, whichever the existing renderers use), never ÷ the sum of the distribution. The same
    applies to any "response %" figure.
